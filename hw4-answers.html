Homework 4: Virtual Memory and Scheduling

Answers of Justin Saldana

Problem 1Page tables of every shape

Sizes in this problem use powers of two: 1 KiB = 1,024 bytes, 1 MiB = 1,024 KiB, 1 GiB = 1,024 MiB. Memory is byte-addressable (every byte has its own address).

For parts (a) to (c): a computer uses 32-bit virtual addresses, 4 KiB pages and page table entries of 4 bytes.

(a) How many pages does one process's virtual address space hold? How large is a single-level page table with one entry for every one of those pages, in bytes and in MiB, and how many 4 KiB pages does that table itself fill?

Offset = log2(4096) = 12 bits; virtual page number = 32−12 = 20 bits. Pages = 2^20 = 1,048,576. Single-level table = 2^20×4 = 4,194,304 bytes = 4 MiB. Its own page count = 4,194,304/4096 = 1,024 pages.

The root table always exists and fills one page. A second-level table, also one page, exists only if at least one page it maps is in use. A process uses exactly three regions of its address space:

(d) A 64-bit processor uses 48-bit virtual addresses, 4 KiB pages, 8-byte entries and a four-level table: four 9-bit indices and a 12-bit offset. How many virtual pages does one address space hold, and how large would a single-level table for it be, in GiB? Why does each level use exactly 9 bits? What is the least page-table memory a process needs if it uses exactly one page?

Virtual page count = 2^(48−12) = 2^36 = 68,719,476,736. Flat table = 2^36×8 = 2^39 bytes = 512 GiB. One 4 KiB table holds 4096/8 = 512 = 2^9 entries, hence 9 bits per level. One mapped page needs one table at each of four levels: 4×4096 = 16,384 bytes = 16 KiB of page-table memory (plus the data page).

(e) A machine with 8 GiB of main memory and 4 KiB frames uses an inverted page table whose entries are 16 bytes (page number, process ID, control bits and a chain pointer). How many entries does it have, how large is it, and what percentage of main memory is that? How does its size change if the number of running processes grows from 10 to 500, and why? Why does the lookup need a hash function and chains?

An inverted table has one entry per physical frame: 8 GiB/4 KiB = 2^21 = 2,097,152 entries. Memory = 2^21×16 = 2^25 bytes = 32 MiB; fraction = 16/4096 = 0.390625%. It remains 32 MiB when processes increase from 10 to 500 because physical frame count is unchanged; it does not allocate a full table for every process’s virtual space. Lookup starts from (process ID, virtual page number), not a physical index. Hashing quickly locates likely entries, and chains resolve keys sharing a bucket.

Problem 2The TLB and the cost of a memory reference

Searching the TLB takes 2 ns and one access to main memory takes 80 ns. On a TLB hit, a reference costs the TLB search plus one memory access for the data. On a TLB miss, it costs the TLB search, then one memory access for every level of the page table (to read the entries), then the memory access for the data. Ignore memory caches. Ignore page faults in (a) and (b).

(b) Why does a good TLB hit ratio matter more with a four-level table than with a single-level one? Why must the TLB be emptied, or its entries tagged with an address-space ID, when the OS switches from one process to another?

Hit cost = 2+80 = 82 ns. Miss cost is 2+80L+80 for L levels, so average = 82+(1−h)80L. A single-level miss adds 80 ns; a four-level miss adds 320 ns, making a high hit ratio especially valuable. TLB entries contain translations belonging to an address space: two processes may use the same virtual page number for different frames. Flush entries on a switch, or tag them with an address-space ID, to avoid using the previous process’s translation or access rights.

4 KiB pages waste far less space at these region boundaries (4 KiB versus 4092 KiB) and allow fine-grained allocation. Large pages greatly increase TLB reach and shrink page-table demand, helping large contiguous working sets. With a fixed physical allocation, larger pages mean fewer resident pages; each brings in more unneeded bytes, and scattered useful references can displace one another. Page size therefore trades locality and transfer efficiency against internal waste and resident coverage, rather than monotonically lowering faults.

(c) Give each policy's total number of faults. Then look at reference 6 (page 4): which page does FIFO evict there, which does clock evict, and why does clock make the better choice? Why does LRU come closer to OPT than FIFO does on this string?

At reference 6 FIFO evicts page 2, which has been resident longer than pages 1 and 3, even though page 2 was just used at reference 5. Clock instead evicts page 1: its bit was cleared during the sweep at reference 4; page 2’s intervening hit set its bit back to 1, giving it a second chance. Page 2 is needed again at reference 7, whereas page 1 waits until reference 8, so clock’s choice avoids the next immediate fault. LRU tracks recent use and keeps repeatedly referenced pages 2 and 4; FIFO ignores hits and can throw out a hot page. On this string the fault totals are OPT 7, LRU 9, FIFO 11, clock 10.

(d) (i) A process faults on page 17, which was evicted 30 ms ago and is still on the free page list. What does the OS do, and why is that so much faster than an ordinary fault? (ii) With demand cleaning, a fault picks a victim page that has been modified. How many disk transfers does the faulting process wait for, and why? (iii) What can precleaning waste, and how does page buffering get the advantages of both?

(i) If page 17’s frame has not been reused, remove it from the free/standby list, restore its mapping, and return it to the resident set: a soft fault with no disk read. (ii) Demand cleaning of a dirty victim requires two disk transfers before the new page is ready: write out the modified victim, then read in the faulted page. (iii) Precleaning can write a page that is later modified again, wasting I/O. Page buffering places replaced clean and dirty pages on separate lists, retaining contents for fast reclamation; a background writer batches dirty pages into clean reusable frames. Faults can use already-clean frames without waiting for a write, while recent pages can still be reclaimed before reuse.

(e) A monitor shows: 40 processes in main memory, processor utilization 12%, the paging disk busy 97% of the time, each process runs only 0.4 ms, on average, between page faults, while servicing one fault takes 6 ms. What is happening, and what should load control do about it? Explain using the rule that keeps the mean time between faults equal to the mean time to service a fault. If the OS decides to suspend one process, give one advantage and one drawback of suspending (i) the process that just faulted and (ii) the process with the smallest resident set.

This is thrashing: CPU utilization is low while paging dominates, with mean time between faults L=0.4 ms much less than fault service time S=6 ms. Load control should suspend enough processes to lower multiprogramming and give remaining processes more frames until L rises toward S; admitting more processes would worsen it. The L≈S rule is a control target, not a claim that exactly 15 processes must be removed.
(i) Suspending the just-faulted process is convenient because it is already blocked and needs no extra interruption; its lack of frames may be temporary, and its resident pages may not be the most useful reclamation target. (ii) Suspending the smallest resident set is cheap to swap and later restore, but frees the fewest frames, so several suspensions may be needed. Either choice must consider importance and likely working-set needs.

(b) The kernel needs 10,000 objects of 200 bytes each. A lazy buddy allocator defers or avoids immediate recursive coalescing on every free. It keeps small free blocks available for quick reuse and merges when larger blocks are needed or a threshold is reached. This avoids repeatedly merging and then splitting the same popular block sizes.

(c) Linux. (i) Linux writes its page-table code for four levels (PGD, PUD, PMD, PTE). How does the same code run on a processor whose hardware has only two levels? (ii) Linux keeps an active list and an inactive list of pages. Describe what happens to a page on the inactive list that is referenced once, and then referenced again, and say from which end of which list the kernel takes pages when it needs free frames.

(i) Fold hardware-unused intermediate levels into effectively one-entry/pass-through levels. The architecture’s page-table helper definitions make the generic walk skip those levels without allocating actual intermediate tables. This answers the four-level model in the question; newer kernels can expose an additional P4D level. (ii) In the traditional active/inactive model, the first reference sets the referenced marker on an inactive page; a later qualifying reference promotes it to the active list, giving repeatedly used pages protection. Reclamation chooses old pages at the tail of the inactive list; active pages age or move back to inactive when not recently used. This is the textbook two-list policy rather than a description of every modern reclaim configuration.

Reserving claims a virtual-address range without committing backing storage; committing makes pages usable and accounts for backing capacity, although physical frames need not appear until touched. Under memory pressure, Windows trims working sets: removed clean pages generally go to the standby list, and dirty pages to the modified list for later writing. (e) Android phones usually have no swap area on their flash storage. Give two reasons. What does Android do instead when memory runs low, in what order, and what must every app therefore be ready for?

Under the question’s no-flash-swap design, frequent paging writes would wear flash and disk-style swapping would add latency, I/O and battery use. First reclaim clean file-backed/cache pages that can be read again and ask apps to trim unneeded caches. If pressure persists, kill the least important cached/empty background processes, then less expendable background/service processes before visible/foreground work, following process importance. Apps must save restorable state and tolerate background termination followed by recreation. Modern Android commonly also uses compressed swap in RAM (zRAM), so “no flash swap” does not mean “no swap of any kind.”

(d) A system has four priority queues, RQ0 (highest) to RQ3, and always runs the first process of the highest non-empty queue. A long background job sits in RQ3. A new job enters RQ0 every 5 ms, and each needs exactly 5 ms of processor time. What happens to the background job, and why? Describe one change to the policy that guarantees it eventually runs, and say what preemption costs the system each time it happens.

The RQ3 job starves: every 5 ms, another RQ0 job replaces the one just completed, so a higher-priority queue is always ready. Add aging, promoting a waiting job to the highest queue after a bounded interval and placing it in a fair FCFS order, or periodically boost all jobs. Each preemption saves/restores registers and scheduling state, updates queues, and disrupts caches/TLB locality; that overhead consumes time without doing the application’s work.

  • RR q = 1: when the quantum runs out, the running process goes to the back of the ready queue; if no other process is ready, it simply keeps running.
  • SPN and HRRN choose only when the processor becomes free, and never preempt. HRRN picks the largest ratio R = (w + s) / s, where w is the time waited so far.
  • SRT always runs the process with the least remaining service time; a new arrival preempts only if its remaining time is strictly less.
  • Feedback, q = 1: queues RQ0 (highest), RQ1, RQ2, … with as many levels as needed, each first-come first-served. A new process enters RQ0. After each unit of running, an unfinished process moves down one queue, unless no other process is ready at that moment (a process arriving at that same moment counts as ready), in which case it stays where it is and keeps running. The processor always takes the first process of the highest non-empty queue.
  • Ties in SPN, SRT and HRRN go to the process that arrived earlier.
  • Turnaround time Tr = finish time − arrival time. Normalized turnaround = Tr / Ts (1.00 is the best possible).

B-b Experiment 1, the string with locality. Rank the four policies from fewest to most faults at 2 frames and at 10 frames. Explain why LRU comes closest to OPT, and why FIFO falls behind most clearly once there are enough frames to hold a working set. At about how many frames does adding a frame stop helping much, and how does that connect to the working sets that locality_refs builds?

At 2 frames: OPT 1440 < LRU 1889 < FIFO=clock 1918. At 10: OPT 238 < LRU 336 < clock 362 < FIFO 440. LRU keeps recently reused locality pages; OPT knows exactly which pages will be needed next, so LRU approaches it without future knowledge. FIFO can evict an old but heavily used working-set page because hits do not refresh its order; clock’s use bits partially repair that. Diminishing returns become clear around 6–7 frames: locality working sets contain 3–6 pages, while extra capacity handles stray references and phase changes. Adding frames beyond that still helps, but much less than the first few additions.

B-c Experiment 1, the uniform random string. Why are FIFO, LRU and clock almost exactly equal here, and why do their counts fall only slowly as frames are added? Estimate the fault count for 10 frames from the fraction of the 40 pages that fit in memory, and compare with your output. Why does OPT still do much better?

With independent uniform references, every one of 40 pages has the same chance of being next. Recent use and age give FIFO/LRU/clock almost no predictive information, so they produce similar counts.
